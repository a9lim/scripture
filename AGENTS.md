# Scripture

A reader for sixteen public-domain sacred works at a9l.im/scripture: chapter and
verse deep links, full-text search, an exact-word concordance, TF-IDF related
passages, notes and bookmarks, text-to-speech, and plaintext downloads. Vanilla
ES modules with no runtime dependencies (OpenDyslexic loads from jsDelivr only
when selected); the corpus is static JSON generated by a Python pipeline in
`extract/`. It is a submodule of the a9l.im repository (`a9lim.github.io`, at
`projects/scripture`); the root `AGENTS.md` covers the shared layer, design
system, build, and deployment.

## Running and checking

Static preview from the parent build serves `http://localhost:8000/scripture/`
only; deep routes such as `/scripture/ot/gen-1` and their SSR need the Worker
(`./dev.sh` in the parent).

```bash
for f in main.js src/*.js; do node --check "$f"; done   # no linter or JS test suite
extract/run.sh verify      # 16 works, 121 books, 2,724 chapters, 63,141 verse records
extract/run.sh pipeline    # full rebuild from raw/, about 50 s
```

`pipeline` reads `raw/`, which is gitignored: a fresh clone has no sources.
The pipeline is deterministic: run on a copy of `extract/`, `raw/`, `data/`,
and `text/`, it reproduces the
committed `data/` and `text/` byte for byte, so after a parser change
`git status` shows exactly what the change did. Python dependencies: PyMuPDF
(`extract/requirements.txt`), scikit-learn for `similarity.py`, and
cloudscraper with beautifulsoup4 for `scrape_sacred_texts.py`.

## How it works

### Data model

- `data/works.json` is the display order for pickers and filters.
  `search_index.py` keeps the existing order and appends new works at the end.
- `data/{work}/manifest.json` is `{ id, title, books, translations? }`; each book
  is `{ id, name, abbrev, chapters, start?, names? }`. `chapters` is a count, and
  chapter IDs are derived as `{bookId}-{start + i}` (`chapterIdAt`, default
  start 1): `gen-1`, `1-ne-3`, `kjk-0`. `names[i]` is an optional chapter
  subtitle. The reader does not read `translations`; it is provenance metadata.
- `data/{work}/chapters/{chapterId}.json` is `{ sections: [{ startVerse, verses }], intro? }`.
  A record's verse number is `startVerse + index`. Multi-section chapters render
  numbered section headings. `intro` is supported but no chapter uses it.
- A ref is `workId:chapterId:verse` (`ot:gen-1:26`); notes, bookmarks, search,
  concordance, and note links all key on it. The URL form is
  `/scripture/{workId}/{chapterId}[:verse]`.
- Chapter titles are built, not stored (`renderChapter`, mirrored in
  `related.js` `getChapterTitle`).
- Indexes: `search-index.json` (`[{ ref, text }]`, one row per record, ~14 MB),
  `concordance.json` (`{ word: [ref] }`, lowercased tokens minus stopwords and
  one-letter words, ~14 MB), `similarity.json` (`{ chapterId: [{ ref, score }] }`,
  chapter-level refs `work:chapter`).

### Client

- `init()` loads `works.json` and every manifest (building `bookMap`), wires the
  modules, then `routeFromPath()`. A bare `/scripture/` opens the latest history
  entry, else the first Book of Mormon chapter.
- `navigate()` `replaceState`s the URL, syncs the pickers, then loads and renders
  the chapter, notes, history, progress, related passages, and prev/next links.
  Chapters are fetched on demand and cached.
- `concordance.json` is fetched at startup so indexed words get `.conc-word`
  after every render (a MutationObserver on `#verses`). `search-index.json` is
  fetched on first search, random verse, word click, or resume dropdown, then
  shared. `similarity.json` loads with the first chapter.
- Search is a case-insensitive substring scan returning the first 100 matches.
  `?q=` opens it prefilled; the Worker's `SearchAction` targets that.
- localStorage keys: `scripture-user` (notes and bookmarks by ref),
  `scripture-display`, `scripture-history` (last 10 chapters), and
  `scripture-theme`. Export/import covers the first three, merging or replacing.

### Serving and SEO

- `wrangler.jsonc` sends `/scripture` and `/scripture/*` to the Worker first,
  except `/scripture/*.js`, `*.css`, `*.md`, `data/*`, and `text/*`, which are
  served as static assets.
- `worker/index.js` answers every other `/scripture` path with
  `/scripture/index.html` and logs a page view. For work IDs in its
  `WORK_TITLES` table it rewrites the head (title, description, Open Graph,
  Twitter, canonical) and fills `#breadcrumb` and `#verses`: a work page lists
  books and chapters with Book, Dataset, and breadcrumb JSON-LD; a chapter page
  renders the first 25 records, or the single linked record, with Chapter,
  Book, Quotation, and breadcrumb JSON-LD; `/scripture/` lists the works with
  CollectionPage and Dataset JSON-LD. Other paths get the unmodified page with
  status 200. The client clears `#breadcrumb` and replaces `#verses` on its
  first render.
- Edition, translator, Wikidata, and `sameAs` metadata per work live in the
  Worker (`WORK_SCHEMA`, `WORK_MENTIONS`), not in the manifests.
- The parent build copies `about.md`'s `title`, `description`, and `updated`
  into the staged `index.html` and `main.js` (`lastUpdated`) and into root
  discovery files, and builds `sitemap-scripture.xml` from the manifests.
  Because the Worker rewrites the head on every route it handles, the about.md
  title and description reach visitors through the static JSON-LD and
  discovery files, not the served `<title>`.

### Data pipeline

`extract/run.sh` stages, each runnable alone: `extract-raw` (all parsers, then
`search_index.py`), `verify`, `json2txt`, `enrich` (`concordance.py`,
`similarity.py`); `pipeline` runs those four in order. Also `reindex`,
`concordance`, `similarity`, `txt2json`, and `scrape <sacred-texts index URL>`.

- `extract.py <source> --parser <name> --output <dir>` runs a parser from the
  registry in `parsers/__init__.py`. Parsers return `[{ manifest, chapters }]`
  and `BaseParser.write_output` writes them. `quad` reads the LDS quad PDF via
  PyMuPDF (`pdf_parser.py`) and emits `ot`, `nt`, `bom`, `dc`, and `pgp`; the
  rest are plaintext parsers, one per work.
- `parse_scraped.py` reads `scrape_sacred_texts.py` output (`=== CHAPTER N ===`
  blocks) for Mencius and the Lotus Sutra, starting a new section whenever verse
  numbers restart at 1. Mencius is added as a book to the existing `fourbooks`
  manifest, so it runs after the `fourbooks` parser.
- `quad` and `kjv-vpl` title-case `LORD`/`GOD` (`normalize_divine_names`).
- The Quran parser rewrites Pickthall's Arabic names and terms:
  `_TRANSLATIONS` maps them to English or biblical equivalents (Allah to God,
  Qur'an to record, Hud to Lehi) and `_SPECULATIVE` to pseudo-Hebrew coinages
  (Mecca to Maccah, Ramadan to Ramazon); `_surah_names.py` overrides surah
  titles to match. Replacement is plain `str.replace` in dict order, so earlier
  entries feed later ones. `docs/quran-arabic-phrases.md` tabulates every
  replacement; `docs/word-correspondence.md` is the sound-correspondence system
  the coinages are derived from.
- `verify_data.py` checks that each manifest's ID matches its directory, that
  every derived chapter file exists and has no empty records, and chapter and
  verse counts against canonical tables for the Book of Mormon, D&C, Pearl of
  Great Price, OT, NT, Quran, and Apocrypha.
- `json_to_txt.py` writes `text/{work}.txt` with a CC BY-SA header, in this
  format (`txt_to_json.py` reads it back):

  ```
  WORK: id | Title
  BOOK: id | Name
  START: N                  first chapter number, when not 1
  CHAPTER: [name]
  > intro text
  @ N                       first section starts at verse N
  SECTION:                  section break, numbering continues
  SECTION: @                section break, numbering restarts at 1
  SECTION: @ N              section break, numbering starts at N
  verse text, one record per line
  ```

- Not in `run.sh`: `patch_vpl.py` (idempotent archaic-spelling fixes written
  into `raw/eng-kjv_vpl.txt` in place), `patch_bom.py` (patches
  `raw/bom.txt`, which no parser reads), `migrate_manifests.py` (a manifest
  migration the committed data already reflects).

Adding a work: write a parser (registered in `parsers/__init__.py`) or scrape
into `raw/`; add its step to `extract-raw`; add its book abbreviations to
`ABBREVS` in `txt_to_json.py` (the text format carries none); run `pipeline`;
place it in `works.json`. The client needs no changes, but the Worker needs
`WORK_TITLES` and `WORK_SCHEMA` entries before its routes get SSR, and
`about.md`, `README.md`, and `index.html` (FAQ, Dataset, `.edu-content`) list
the works and their counts by hand.

## Conventions

- Work IDs match `[a-z]+` (the Worker's route regexes). Book IDs match
  `[a-z0-9-]+` and are unique across all works: `bookMap` and `similarity.json`
  key on them without a work prefix, and note text links refs with
  `[a-z]+:[a-z0-9-]+-\d+:\d+`.
- `data/` is generated from `raw/` and `text/` from `data/`; fix a text problem
  in its parser and re-run. `txt2json` reproduces `data/` except each manifest's
  `translations` (`json_to_txt.py` writes no `TRANSLATION:` lines), so
  `extract-raw` is the reproducible path.
- Writers overwrite chapter files but never delete them, and the index builders
  read every file in `chapters/`, not the manifest. When a parser change renames
  or drops chapters, clear that work's `chapters/` before re-extracting
  (`fourbooks` needs both its parser and the Mencius step).
- Client fetches use absolute `/scripture/data/...` paths: the page usually sits
  at a deep route, where a relative URL resolves under `/scripture/{work}/`.
- `#verses` and `#breadcrumb` are the Worker's SSR targets. The Worker's
  single-verse SSR indexes the flattened record list (`n - 1`), which agrees
  with the client only when numbering starts at 1 and never restarts.
- Renaming `scripture-user` orphans every saved note and bookmark. `notes.js`
  still migrates the older `scripture-notes` key on first load.
- Licensing has two layers: the application is AGPL-3.0; the text downloads and
  the structured arrangement are CC BY-SA 4.0 (`text/LICENSE`), with the
  historic source texts treated as public-domain inputs. The corpus is described
  with its CC BY-SA license, not the Public Domain Mark.
- `#toolbar` overrides `base.css`'s initial `opacity: 0` (the shared intro
  reveal); scripture has no intro screen.
- `--toolbar-h` (96px once the toolbar wraps to two rows at 900px and below)
  drives the layout offsets; an open TTS bar adds 36px through
  `body:has(.tts-bar:not([hidden]))`. Verse numbers sit in `#reading-pane`'s
  left padding through a negative margin, so those two values move together.
  `#reading-pane` is `position: relative` because the concordance popover is
  positioned inside it.
- The reader font setting applies only to verse text (`--reader-font-family` on
  `#reading-pane`); verse numbers and chrome stay on `--font-text`.
  `--font-reader-sans` is a local system stack, nothing downloaded.

## Open work

- Mencius (170 sections) and one Lotus Sutra chapter restart verse numbering
  within a chapter, so 690 records share a ref with an earlier record. They
  cannot be linked, noted, or bookmarked separately, and their `#v{n}` ids
  collide. Separately, `add-esth-10` starts at verse 4, so the Worker's
  single-verse SSR shows the wrong record there.
- The Quran `jinn` to `genies` replacement also rewrites `jinni` as `geniesi`
  (55:39, 55:56, 55:74).
- `concordance.json` (~14 MB) is downloaded on every visit to mark indexed
  words, before any word is clicked.
- The full concordance overlay has no Escape handler (search, popovers, and
  dropdowns do).
- `verify_data.py`'s docstring lists checks it does not run (manifest verse
  counts, sequential numbering, `startVerse` consistency).
- `extract/requirements.txt` lists only PyMuPDF.
